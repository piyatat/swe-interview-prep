# Canonical engineering track

Sits beside [redhat.md](redhat.md): **Ubuntu / open-source company, fully distributed for 20+ years**, not Red Hat’s IBM-owned enterprise loop and not a FAANG onsite. Official [hiring process](https://canonical.com/careers/hiring-process) is the source of truth. Recruiter here is a **Hiring Lead** (a business-function leader, not an early-stage HR filter). They confirm **product vs support vs field**, language, and that assessments are **unaided**.

Typical official path (~**3 months** application → offer, all levels): application questions → written interview → GIA psychometric → optional domain technical assessment → **three** technical/domain interviews → Talent interview (plus 10-min PPA) → late-stage manager / Hiring Lead / seniors (CEO if you lead people) → offer. Pair: [../general/pair-programming.md](../general/pair-programming.md). Comp: [../general/offer-negotiation.md](../general/offer-negotiation.md).

## Official culture (signals they publish, not invented LPs)

Do **not** paste Amazon principles. Official hiring page scores people who thrive **distributed and global**.

| Official signal | Prep one-liner |
| --- | --- |
| **High academic performance + initiative** | Evidence from school **and** later drive; they ask both |
| **Cognitive ability / trainability** | GIA is required for **every** applicant |
| **Drive, curiosity, stamina** | Ground-breaking work, not ticket-closing theater |
| **Own words, no online aids** | Written + live: your thinking, not a model |
| **Fair global process** | Same stages so location is not an advantage |

“Why Canonical?” that only says “I use Ubuntu / I want remote” fails. Name a **packaging, distro, OpenStack/K8s, or upstream** problem you have lived. Official: they have run a fully distributed company for **over 20 years**; multicultural, many time zones.

## Official process

Official [hiring process](https://canonical.com/careers/hiring-process). **Hiring Lead** owns you end-to-end. Domain experts — not HR recruiters — make the early yes.

| Stage | Official |
| --- | --- |
| Application | Via the **job advert**; extra questions. **Once per job / 180 days**, or **4 jobs / 180 days** |
| Dashboard | If they proceed: personalized assessment plan |
| Written interview | Same questions for everyone in the role; **anonymous** review (no resume); typically **two** domain graders; you pick format/length |
| GIA | **30–45 min**, five parts: aptitude, problem solving, speed of learning. **Not an IQ test.** Required for all |
| Technical assessment | Role-specific; graded by a domain expert; they will **open it** in later interviews |
| Early interviews | **Three** technical/domain hours with future colleagues |
| Talent interview | Career motivations; **10-min Personality Profile Analysis** first; **comp philosophy** starts here |
| Late stage | Potential manager, Hiring Lead, seniors; **CEO** if management/leadership |
| Offer | Hiring Lead; then New Joiner / onboarding |

Official: use **your own words without online aids** in assessments and interviews. Average **~3 months** graduate through VP. Confirm `@canonical.com` (fraud FAQ on the same page).

Guides (Ubuntu eng blog on written interviews; Calibrd / PracHub 2026): treat **question counts** (long written packets, Thomas GIA subtests, 90-min coding) as **reported**. Budget **several evenings** for the written; they grade substance, not speed-typing.

## How this track differs

| vs Red Hat / FAANG | vs typical startup |
| --- | --- |
| Official **written + GIA before any video** | No “quick 30-min screen then onsite” |
| Official **~3 months**, Hiring Lead not TA recruiter | Exploding offers elsewhere — tell them, but do not expect a two-week loop |
| Academic + cognitive screens **at every level** | “I only grind LeetCode” misses the written |

## Coding and design flavor

Official technical assessment is **domain** (packaging, Python/Go, Linux) and they will probe the submission later. Live hours: architecture, Linux/open source, the team’s domain. Design: image/signing, upgrade reversibility, fleet of Ubuntu. Related: [../roles/devops-sre.md](../roles/devops-sre.md), [../roles/platform.md](../roles/platform.md), [../general/low-level-design.md](../general/low-level-design.md).

## Sample prompts (shapes, not leaked puzzles)

1. Why **this** Canonical product (Ubuntu, MAAS, Juju, Anbox, …) — portable “I like Linux” is weak.
2. Written: architecture tradeoff **in your words**; one specific result, not a blog summary.
3. GIA: timed accuracy; rest; do not treat it as trivia.
4. Technical: defend the assessment; Linux / packaging / API design follow-ups.
5. Questions: which team after the three technicals, GIA vs written weighting, remote hubs.

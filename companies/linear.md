# Linear engineering track

Sits beside [asana.md](asana.md) and [notion.md](notion.md): **issue / product workflow craft**, not a generic SaaS slate. Official [How we hire](https://linear.app/now/how-we-hire-at-linear) (2026-04-28): small, **profitable**, hire slowly; **slope over credentials**; interviews under-index talkers, so the closer is a **paid work trial**. Official [Careers](https://linear.app/careers): mission is to **inspire and accelerate builders**; fully remote. Recruiter confirms **eng vs design**, TypeScript / sync vs infra, and trial length.

Typical timeline **4–6 weeks** (official). Take-homes / trials: [../general/take-homes.md](../general/take-homes.md). Pair: [../general/pair-programming.md](../general/pair-programming.md). Sync cousin: [../answers/system-design-collab-editor.md](../answers/system-design-collab-editor.md). Comp: [../general/offer-negotiation.md](../general/offer-negotiation.md).

## Official hire bar (do not invent extra pillars)

Official How we hire attributes + [careers principles](https://linear.app/careers). They do **not** use OKRs or A/B tests — decisions are **taste + customer insight**. Map **your** stories.

| Official signal | What they score |
| --- | --- |
| **Craft** | Depth and details that matter; quality ≠ extra busywork |
| **Judgment** | Tradeoffs with incomplete data; unpolished but sound |
| **Ownership** | End-to-end; users, direction, progress — no PM script |
| **Clarity** | Simple speech; respect other people’s time |
| **Fit with how we work** | Small team, high standards, build > manage |
| **Slope over credentials** | Fast growth + clear thinking beats logos |

Careers principles to know (not a second LP list): **Ship early**, **Build with users**, **Know what good looks like**, **Think in principles**, **Build things that last**, **Avoid side quests**, **Say it as it is**, **Keep the team small**, **Hire the best**, **Create fans**, **Fully remote**.

“Why Linear?” that only says “I use the app / I hate Jira” fails. Name a **latency, sync, or issue-state** problem you have lived.

## Official + reported process

Official How we hire is the skeleton. Official [work trials](https://www.linear.app/now/why-and-how-we-do-work-trials-at-linear): trial is the **final** step, only when they already want to work with you. 2026 TechPrep adds a take-home / onsite split — treat extra stages as **reported**.

| Stage | Official / reported |
| --- | --- |
| Application / Talent review | Careers page, sourcing, referrals — same path after |
| Early conversations | Recruiter and/or HM; **comp on the first recruiter call** (official) |
| Team interviews (official: most roles **3–4** talks before trial) | Eng: coding, architecture, design decisions |
| Work trial (official, **all roles**, **paid** 2–5 days) | Real project, internal tools, kickoff / candidate-led check-in / presentation |
| Decision | Independent written feedback → **blind vote** → HM call; prefer unanimous |

Official: they pay a **daily rate** up front; flexible scheduling (sometimes weekends). After trial they give **honest feedback** even on a no. TechPrep: applied TS modeling (issue state machine) and a 4–8h take-home — **ask**; do not assume a second unpaid project.

## How this track differs

| vs Asana / Notion | vs FAANG web |
| --- | --- |
| Official **paid 2–5 day trial** is the closer, not another puzzle loop | Design is **local-first sync / issue graph**, not “design Twitter” |
| No OKRs / A/B; taste is a scored skill | Comp is discussed **early** (official) |
| Small remote team; fewer meetings, more surface area | “I only grind LeetCode” misses craft + trial |

## Coding and design flavor

Applied TypeScript, state machines, graphs of issues / comments. Design: sync engine, conflict, optimistic UI. Related: [../answers/coding-course-schedule.md](../answers/coding-course-schedule.md), [../answers/system-design-collab-editor.md](../answers/system-design-collab-editor.md).

## Sample prompts (shapes, not leaked puzzles)

1. Why **this** builder tool — portable “issue tracker” is weak.
2. Live: model issue transitions + blocked states; name the invariant first.
3. Design: offline client writes that collide — last-write-wins vs CRDT, and what users see.
4. Judgment: a time you **did not** ship because quality was not there.
5. Questions for them: trial vs any take-home, AI-in-trial (guides: allowed if you steer it), team size.
